# Data rules

**Main only, and only the sections main's row in the `agent-briefs.md` reading map names.** Gatherers never open this file; they get its conventions inline in their brief and its direct-connection section only where the map says so. It holds the conventions, the id kinds, the region rules, the direct-connection call shapes, and (second half) which source answers which question plus the traps that make a wrong number look right. Query slugs are owned by the file the subagent table in `SKILL.md` names, and each query file's headings are its own index.

The other three (`queries-account.md`, `queries-products.md`, `queries-money.md`) are read by whoever runs their queries: **each gathering subagent opens only the sections its reading-map row in `agent-briefs.md` names**, and a single-threaded run reads all three here in one parallel batch. Every heading is self-contained enough to run from, so opening one whole is waste rather than thoroughness.

Almost every query runs against **project 2** via the PostHog MCP `execute-sql`. Two exceptions: EU experiment definitions, which need EU project 1 and a separate key (see Regions below), and the customer's own raw product events, which come from the direct ClickHouse connection in either region by passing `connectionId` to the same tool (see "The direct ClickHouse connection" below). The call shape is `call execute-sql {"query": "..."}`, with `connectionId` as a sibling key for the direct connection. **Do not run `info execute-sql`**: it returns several thousand words of schema documentation that this file already covers, and it costs a full round trip before the first query. The shape above is all you need, and `scripts/phq.py` needs no schema at all. Prefer more queries over fewer; they parallelize. For any request, always verify with real data.

## Conventions

- Substitute `<ORG_ID>` with the customer's PostHog org ID (Vitally `accounts[0].externalId` or `traits.organization_id`), single-quoted.
- `<days>` defaults to 30 everywhere. A query that deliberately fixes a longer window states it inline beside its own SQL, with the reason.
- Other placeholders: `<domain>` (an email domain, no `@`), `<VITALLY_ACCOUNT_ID>` (the Vitally account id from Step 1, not the PostHog org id), `<id1>`/`<id2>` (Vitally conversation ids).
- Org scope is `$group_0 = '<ORG_ID>'`, with no exceptions. It is a strict superset of `person.properties.organization_id`, which only ever loses rows. `properties.$group_0` and the bare `$group_0` column return identical rows, so every MCP query here uses the bare column: the `properties.` form also trips a spurious taxonomy warning. The saved-insight form below is the one place `properties.$group_0` is correct.
- **Put `team_id` in the SELECT of every `events` query and read the value back.** Project 2's `events` scoped by `$group_0` returns `team_id = 2`, the customer's admins clicking around the PostHog app, never their product. The source-kind table under "What we can and cannot see" says the same thing as a fact; this line is the mechanical check, and it is the only one that catches the case on an event name that exists in both worlds (`$feature_flag_called`, `$pageview`, `$identify`, `$autocapture`), where the result reads as a plausible answer to the question you asked.
- **Person accessor: use `person.properties.email`** (all queries are standardized to `person.`).
- **Probe an unfamiliar table with `SELECT * FROM TABLENAME LIMIT 100` only the first time a run touches a table it has no recipe for.** Recipes run verbatim need no probe. Never probe `vitally.users` or `zendesk_tickets_by_org`: both time out on unbounded reads.
- HogQL quirks: **always alias `team_id` to `team`.** Unaliased it can 400 as a reserved word on the EU project 1 endpoint while the project 2 MCP path tolerates it, so the alias is the one form that works everywhere. Never let an unaliased `team_id` be your explanation for a result you did not expect; cast with `toInt(...)` not `toInt64(...)`; `variables.*` fails via MCP (use the literal org id); test a `properties.*` field for presence with `IS NULL` / `IS NOT NULL` (or the equivalent `isNull()` / `isNotNull()`, which behave identically), and never with `!= ''`, which errors on a typed field and counts absent keys as present on an untyped one; JSON functions (`JSONExtractKeysAndValuesRaw`, `JSONExtractArrayRaw`) error on nullable columns with "Nested type cannot be inside Nullable", wrap with `coalesce(toString(col), '[]')`; `system.ingestion_warnings` is project-scoped, so it is not reachable from project 2: report it as not readable rather than as zero warnings.
- **Project 2 reports timestamps in US/Pacific, so every date you read is Pacific unless you converted it.** An evening Pacific timestamp is already the next calendar day for a European customer, so a date lifted straight out of a result and pasted into a draft is regularly wrong by a day. Convert to the customer's own timezone before any date reaches a brief or an email, and say which timezone a date is in whenever two are in play.
- **Bots are a judgment about who counts as a user, so measure both ways rather than choosing one.** Count filtered and unfiltered in the same query (`count()` beside `countIf(getBotName(properties.$raw_user_agent) = '')`) and report both whenever they differ by more than a few percent, because the gap is a finding rather than noise. `getBotName` is the right function and `$virt_is_bot` / `isLikelyBot` are wrong in either direction: `getBotName('')` returns an empty string, so an event with no user agent is NOT a bot, while `isLikelyBot` reads an absent UA as automation and makes whole server-side products vanish. But `getBotName` has its own failure in the same direction, and it is the one that looks right: an API or agent client sends a real user agent that bot detection classifies as a bot, so on a machine-driven account the filter silently drops the customer's own automation. Measured on Arthos Inc, 2026-08-17: `query executed` read 49,531 filtered against 94,290 unfiltered, and the filtered half was the wrong answer. Bot shares move, so measure the account's own rather than carrying one over.
- Add `LIMIT` to every query: the server caps at 100, max 500.
- **Truncated text is a truncated result, and the LIMIT rule applies to it whole: never read a verdict, and above all never read an absence, out of the visible portion.** Three shapes cause it and they look identical downstream. Wide JSON and array columns (`plans_map`, `custom_limits_map`, `organization_users`, `sales_info`, `traits`, `segments`) are cut mid-value by any multi-column `SELECT`. A `substring(...)` written into a recipe cuts every row at a fixed width, and several recipes here carry one deliberately for a survey pass. And long HTML bodies (conversations, calendar invitations) put the boilerplate first and the content last, so a truncated read returns only the part that is identical on every record.

  The recovery is the same in all three: re-read the one thing you need at full width before it becomes a sentence. `JSONExtractString(coalesce(toString(col), '{}'), '<key>')` or `JSONExtractKeys` for a map, and the same query with the `substring` removed for a body. Do it whenever a claim turns on presence or absence, on a value near the end of a long field, or on anything a customer will read and check.
- **Identical repeated queries return a cached result with a frozen clock**, and only a cache-busted call moves. Two consequences. Any attempt to observe drift by re-running the same query sees none and concludes wrongly that the data is static. And a sliding `now()` window does move a total between distinct calls, by a fraction of a percent, larger in absolute terms on a larger account. Small, but it is why two reads of the same thing rarely tie to the unit: report the share, not the difference, and use a fixed window (`>= '2026-08-04' AND < '2026-08-11'`) when a number has to be reproducible.
- **Two ways a read fails under load, one fix ladder, and never drop the read.** `TOO_MANY_SIMULTANEOUS_QUERIES` (ClickHouse code 202) is a concurrency rejection: the fan-out exceeded the simultaneous-query cap and the extra queries were refused outright, so an identical retry hits the same wall. **Serializing is the RESPONSE to a 202, never the standing posture**: fire the batch, and only if it is refused drop that agent to serial reads for the rest of its brief, because it competes with every other subagent for the same cap. Grouping (the convention above) is the better first move, since a few wide queries fit in one batch where many narrow ones do not. A timeout is the execution ceiling, with one wrinkle: the server can finish the query after the client gives up and cache the result, so retry identically ONCE and take the cached result if it returns instantly; a second identical retry just burns another full wait. Then narrow: **halve the window** first, then **split a query carrying several independent subselects into one query per subselect**. Both recover the same numbers. Only after both fail is a read unmeasurable, and say which fix you tried. This bullet is the one home of the retry rule; the query files defer to it.
- **A DeltaLake kernel error is transient storage, not a dead table: retry it later in the run rather than routing around it.** The shape is `Code: 742. DB::Exception: Received DeltaLake kernel error GenericError: ... No files in log segment (in snapshot)`. It has hit `all_posthog_team` and `eu_postgres_posthog_team` on repeated attempts and then read normally later in the same run. It is not the 202 or the 429 and neither fix ladder applies, because it is not load. Two consequences. It fails a table the whole run leans on, so recover the team ids from the org usage report's `teams` map (`JSONExtractKeys`) and keep going rather than declaring the region unmeasurable. And **do not write the outage into a subagent brief as standing state**: a brief that says "this table is currently broken" makes every downstream agent skip a read that works by the time it runs.

- **The HTTP API path throttles separately from ClickHouse, at a much lower width, on project 2 as well as EU.** On project 2 over `phq.py`, width 8 has returned 429, so **4 is the safe default**. On the EU endpoint a 12-wide batch throttles part of itself. This is not the 202 rule; 202 is ClickHouse concurrency and 429 is the HTTP API rate limit, and the recovery differs: a 429 wants a narrower batch, a 202 wants grouping. So on the EU curl path **batch 4 to 6 wide, not 12**, and expect one widening step in the fix ladder rather than one big block. Where a batch is throttled anyway, serialize the remainder and log the depth overrun; never drop the read.
- **Fire independent queries in one parallel batch, and put slow independent work in a subagent.** These queries do not depend on each other, so batching is what keeps a full call-prep run to a few rounds instead of thirty. The batching rule and what to delegate live in the Step 2 header of `SKILL.md`.
- **Group, never loop.** Where a recipe filters one entity, run it once grouped over all of them rather than once per entity. Almost every recipe here is already org-scoped and needs nothing; the ones that tempt a loop are the direct-connection reads below, because their worked examples show a single `team_id`. Grouping is arithmetically exact against the per-team loop and faster, widening as team count rises because the grouped query's cost barely moves while call count scales linearly. It also gives one read one snapshot. It does NOT give one total: a per-project share still takes that project's own denominator out of the same result.

  **A grouped result manufactures a silent zero, and this is the reason to be careful rather than fast.** A team with no matching row simply does not come back, and two different facts flatten into the same silence: a project that has never sent an event and one that sent events and went quiet. Nothing in the result says which projects were asked about and not answered. The per-team loop does not have this hole, because an empty result is attributable to the team you asked about. A single result-wide `LIMIT` compounds it: under `ORDER BY team` the first team can consume the whole cap while busy projects further down return nothing.

  So group with all three of these, never fewer:

  1. **Seed the zeros in the same query** so every team you asked about comes back, present or not:

  ```sql
  SELECT team, sum(c) AS c FROM (
    SELECT arrayJoin([<TEAM_IDS>]) AS team, 0 AS c
    UNION ALL
    SELECT team_id AS team, count() AS c FROM events
    WHERE team_id IN (<TEAM_IDS>) AND timestamp >= now() - INTERVAL <days> DAY
    GROUP BY team
  ) GROUP BY team ORDER BY team
  ```

  2. **Cap per group** with `LIMIT n BY team`, never one cap across the result, and read a full group as truncated rather than complete. **`LIMIT n BY` does not lift the server's own row cap**, which still applies to the whole result: size `n` so that `n` times the group count stays under the cap you are actually served, or the groups ordered last fall off the end of the result and read as sending nothing. Count the groups you got back against the groups you asked about on every grouped read, and treat a missing group as truncation until a narrower query proves it empty.
  3. **A zero still needs its history.** A team at zero in the window may be dead or merely quiet, and the grouped row cannot tell you which. Widen to 365 days for any team that comes back zero before calling it dead.

  One thing a grouped rewrite must not lose: grouping never crosses the region boundary. Group across one org's teams within one region, never across regions, because the same integer names a different company in the other one (the half-swap rule below).
- **Splitting custom from automatic on the `$` prefix is wrong on mobile.** `Application Opened`, `Application Backgrounded`, `Application Installed`, `Application Updated`, `Application Became Active` and `Deep Link Opened` carry no `$` and are SDK lifecycle autocapture, not instrumentation anyone wrote. The naive split has overstated the custom share several times over on mobile accounts, and has credited a project with custom instrumentation whose real figure was zero. Subtract the lifecycle family before quoting a custom share, and give both numbers when the gap is large. The list is a floor, not a roll call: enumerate the account's own event names and judge each unprefixed one before trusting it as customer instrumentation, because the SDKs keep adding lifecycle names and each new one inflates the custom share in the same direction.
- **Measure SDK version currency over the last day or two, never over the whole window.** A web SDK auto-updates, so a 30-day version histogram counts release history rather than staleness and will show dozens of live versions on a perfectly current fleet. The trailing-2-day share describes their deployment; the 30-day one describes npm's release cadence, and both are true at once. Quote the short window, and only call a fleet stale when the RECENT share is behind. A pinned native or server SDK is the opposite case and the long window is right there, because it does not move on its own.
- **Random or opaque event names mean a variable is being passed as the event name.** Rank the tail of the event catalogue, not only the head, and treat a cluster of same-length nonsense names (`2lowqmW`, `4a7HzCy`) as an instrumentation bug worth reporting. `test` and `test_event` in production belong in the same finding.
- **A paused mirror sync answers exactly like an empty table.** The resolver warns when it happens (`Sync of <table> is paused. Results reflect the last successful sync from N months ago`), and that warning is the only signal: the query succeeds and returns zero rows with no error. Read the warning before reading the result. A paused mirror makes the object **unmeasurable, never zero**, so say so rather than reporting an absence, and cross-check the usage report where it carries a matching count.
- **Every field and table name in these files is a snapshot, so enumerate the live schema whenever the data does not fit it.** PostHog ships new SDKs, products, and usage-report keys continuously and these recipes lag them, so a name that returns nothing is as likely to be stale here as absent there. The sharpest tell is a subset of zeros under a non-zero parent, where the driver sits outside the fields the recipe happens to name: a Flutter or Go account reads as dead against a select listing only the common SDKs. To find what is really there, `JSONExtractKeys(assumeNotNull(properties))` returns every key the usage report carries, `system.information_schema.columns` returns a table's real columns, and the resolver's "Did you mean" list fuzzy-matches real table names. Reach for those the moment a named field comes back empty or a result contradicts what the account plainly does, then report the value you found and say the recipe missed it.
- Two execution forms: MCP uses the literal `$group_0` filter shown in the recipes; to save a query as a parameterized PostHog insight instead, swap the org filter for `AND (coalesce(variables.orgid, '') = '' OR properties.$group_0 = variables.orgid)`.
- Execution fallback (MCP unreachable only; the MCP stays primary): every query also runs over the HTTP API, and `scripts/phq.py` is that path already built, with the endpoint, the key and the payload shape picked per target. `phq.py us "<sql>"` covers project 2 including `eu_postgres_*`, `postgres.prod.billing_customer`, dbt and `vitally.*`; `eu`, `ch-us` and `ch-eu` cover the rest. `--batch <file.jsonl>` fires many at once at a width that respects the EU rate limit, and it retries a throttle or a concurrency rejection once before reporting. `docs-search` has no API equivalent: verify doc links with plain HTTPS fetches of the `posthog.com/docs/...` URLs instead.
- `vitally.accounts.segments` is an array of `{id, name}` objects, not strings. Match on the name: `arrayExists(x -> JSONExtractString(x, 'name') = 'Onboarding referral', JSONExtractArrayRaw(coalesce(toString(segments), '[]')))`. Extracting it as `Array(String)` returns zero rows rather than erroring, so a segment filter written that way silently reports "no accounts". `billing_customer.crm_segments` is the plain string array and does take `Array(String)`.
- Optional staff filter when PostHog staff have been in the customer org (inflates per-session ratios): append `AND person.properties.email NOT ILIKE '%@posthog.com%'`.
- Daily-form variant of any aggregate (for spike/trend detection): add `toStartOfDay(timestamp) AS date`, `GROUP BY date`, `ORDER BY date DESC`.

## IDs (three kinds, and which column matches each)

| Id | Shape | Matches |
|---|---|---|
| PostHog org id | UUID, globally unique | `$group_0` on events; `all_posthog_team.organization_id`; `vitally.accounts.external_id`; `billing_customer.organization_id`; `accounts_replacement_v2.organization_id`. `onboarding_accounts` and `account_health_scores` spell it `org_id` |
| Vitally account id | UUID | `vitally.accounts.id`; `vitally.notes` / `tasks` / `projects` `.account_id`; the Vitally MCP `accountId` (the MCP also resolves org ids) |
| Team id | region-local integer | `posthog_team.id` and the `team_id` columns. The same integer names a different company in the other region, so it never crosses the region boundary |

An id handed in by the user can be either UUID kind: the Vitally MCP resolves both, the warehouse does not. In the warehouse, `vitally.accounts.organization_id` is NULL on every row, so the org-id join there is `external_id` only, and it never matches on name (several accounts share one).

One more join key: `all_posthog_organization.customer_id` carries the Stripe `cus_` id that joins to the invoice tables. The table repeats org rows, so dedupe `customer_id` before joining; the money queries build this in.

## Regions

Detect the region from `vitally.custom.usEuInstance` (an array, e.g. `["US"]`, populated far more widely than the alternatives); fall back to `cloudRegion`, then `traits.site_url`, where `eu.posthog.com` means EU. In the warehouse, `all_posthog_team.app_region` (lowercase `us` / `eu`) is the answer: `resolve-teams` returns it beside the team list.

Swap regions all-or-nothing across every table in a statement, and never carry an integer id across the boundary: the half-swap rule and its damage are below.

The source-kind table, which source answers which question, sits under "What we can and cannot see" below, beside the sentence that reads it.

### The direct ClickHouse connection: reading a customer's OWN product events

A ClickHouse `Production` source is wired into the internal project of **both** regions, and on it `team_id` is a selectable column that is **not scoped to the local project**. So a customer's own raw product events are readable directly, in either region. On it `person_mode` is a plain column on `events`; `properties.$person_mode` is empty on every row. This is the source for per-event-name volumes, the autocapture share, and the identity mix.

**The short path is `scripts/phq.py ch-us "<sql>"` or `ch-eu`**, which carries the connection id and the payload shape for you, and takes `--batch` like any other target. The shapes below are what it sends, kept here for the MCP path and for debugging a 400.

**US customer, from project 2, over the MCP.** Pass `connectionId` as a sibling of `query`:

```
call execute-sql {"query": "SELECT team_id AS team, event, count() AS c FROM events WHERE team_id IN (<TEAM_IDS>) AND timestamp > now() - INTERVAL 1 DAY GROUP BY team, event ORDER BY team, c DESC LIMIT 40 BY team", "connectionId": "019fa95f-caa3-0000-4452-6dc502c7eb96"}
```

**EU customer, from EU project 1, over the API with `POSTHOG_PERSONAL_API_KEY_EU`.** The MCP cannot reach it, so this one is a curl (build the payload per the HTTP rule in `SKILL.md`). **`connectionId` goes INSIDE the `query` object here**, and the two wrong placements both fail loudly: as a sibling of `query` the request 400s with `connectionId Extra inputs are not permitted`, and as `connection_id` inside `query` it 400s the same way. Only the camelCase-inside-`query` form works.

```
POST https://eu.posthog.com/api/projects/1/query/
{"query": {"kind": "HogQLQuery", "query": "SELECT team_id AS team, event, count() AS c FROM events WHERE team_id IN (<TEAM_IDS>) AND timestamp >= now() - INTERVAL 7 DAY GROUP BY team, event ORDER BY team, c DESC LIMIT 40 BY team", "connectionId": "019fd687-7e09-0000-bbf2-cd4fc538c514"}}
```

**The US connection also answers over HTTP at `us.posthog.com/api/projects/2/query/` with the US personal key, `connectionId` inside the `query` object exactly as EU does.** So the direct connection survives the MCP gateway going down in both regions.

**Without `connectionId` the same EU query silently returns zero rows rather than erroring**, because plain EU project 1 `events` is scoped to PostHog's own team 1, so the empty result reads exactly like "this customer sends nothing". Never run a customer `team_id` query against EU project 1 without the connection.

`<TEAM_IDS>` is the org's whole team list from `resolve-teams`, passed as a comma-separated `IN` list so one read covers every project. Substitute a single id only when one project is the target. Get the ids from `postgres.posthog_team` / `eu_postgres_posthog_team`, or from `resolve-teams`. Discover the connection id rather than trusting either literal above if a query fails: US is `call external-data-sources-connections-list {}`; EU is `GET https://eu.posthog.com/api/projects/1/external_data_sources/?limit=100` with the EU key. Take the row with `source_type: ClickHouse` and `prefix: Production`.

**What it covers differs per region, and the only way to know is to query.** The two sources are configured independently, so never carry one region's answer to the other.

| Table | US, project 2 | EU, project 1 |
|---|---|---|
| `events`, `person`, `ai_events`, `log_entries` | readable | readable |
| `session_replay_events` (replay volume and duration) | `Unknown table` | **readable, per `team_id`** |
| `heatmaps`, `sharded_heatmaps` | `Unknown table` | **readable, per `team_id`** |
| `query_log_archive` (the unqueried-events join; singular, no `_us` / `_eu` suffix here) | `Unknown table` | **readable, per `team_id`** |

**Two different tables share this name and one run had two gatherers contradict each other over it. Read this before reporting either as unavailable.** `query_log_archive` on the **direct connection** carries the raw `query` text with literals intact, which is the only thing that can answer "which event names has anyone queried", and it exists on EU only. `query_log_archive_us` / `_eu` in **project 2** is a different table: readable in both regions, carrying `team_id` and the `lc_*` object ids, and it is what the dashboard built-versus-read check uses. It cannot answer the event-name question, because its `query_shape` and `hogql_shape` normalize every literal to `?`, so the event name is stripped before you see it. So "the US query log is unreadable" is wrong and "the unqueried-events join works on US" is also wrong: the project-2 table reads fine and cannot carry that join. Name which of the two you probed whenever you report either one.

So on an **EU** account, replay volume, replay duration and the unqueried-events join all run here, and the replay rule below about reading volume from the usage report applies to **US only**. Cross-check the recording count against `billing_usage_by_org_date` anyway; agreement between the two is what earns the right to quote either.

**Count recordings with `uniqExact(session_id)`, never `count()`.** A session writes many rows to `session_replay_events`, so `count()` is a row count wearing a recording count's name. The gap between them is that account's own rows-per-session ratio, so it cannot be predicted and a `count()` already taken cannot be corrected after the fact. Only `uniqExact` reconciles with the billing table. Use it for every captured-versus-watched ratio and every duration distribution, and never carry one account's observed gap to another as an expectation.

**On EU, `session_replay_events` is readable but three access patterns fail, and the failure looks like the table being broken.** Plain reads (recording counts, active hours, byte totals) work; what fails is specific. The argMin state columns (`snapshot_library`, `first_url`, `all_urls`, `block_urls`) return `AggregateFunction ... deserialization not supported`. `toDate(min_first_timestamp)` returns ClickHouse code 43, where `toStartOfDay()` and `toStartOfMonth()` work. `duration` is unresolvable (HTTP 400): compute it with dateDiff over min(min_first_timestamp) and max(max_last_timestamp). And `information_schema` reports every column on this table as `String`, so it cannot be used to tell a plain column from a state column. So: read plain and simple-aggregate columns, bucket dates with `toStartOfDay`, never trust the reported types here, and do not read a code 43 as the table being unavailable.

**`query_log_archive` retention varies by region and has been measured months apart, so measure it rather than assuming: take `min(query_start_time)` in the same read and quote that span.** The column set is narrow. So the unqueried-events join answers "nobody has queried this in the retained window", never "nobody has ever queried this", and the digest has to say which. Columns that resolve: `query`, `query_id`, `query_start_time`, `query_duration_ms`, `query_kind`, `user`, and the `lc_*` object ids. Columns that do NOT exist despite reading like they should: `query_shape`, `hogql_shape`, `kind`, `query_type`, `user_id`, `access_method`, `is_personal_api_key_request`. Probe before projecting one. Reading `user` is also how you separate a human from `max_ai`, which is PostHog AI querying on their behalf and is adoption evidence rather than noise.

Two naming traps survive in both regions. `raw_session_replay_events` does not exist on the connection at all: it errors with `Unknown table`, and the resolver correctly offers `session_replay_events` (no `raw_` prefix). `property_definitions` resolves, holds billions of rows, and **does return a customer's own rows**, so it IS the EU property-definition source, reached through the connection rather than through a mirror. It is also a frozen snapshot, so any EU team created after its `team_id` ceiling reads zero rows. Probe the table's max `team_id` before reading an empty result as no properties.

**Do not read the enabled state off the sources API.** `GET /api/projects/1/external_data_sources/` returns a `should_sync` flag per schema, and on EU it reads `true` on every one of them with `status` and `last_synced_at` null, including tables that error on query. The flag describes the catalog, not access. A `SELECT count() FROM <table> LIMIT 1` is the only reliable test, and it costs one call.

Anything missing is one toggle away on the source schemas page ([US](https://us.posthog.com/project/2/data-management/sources), [EU](https://eu.posthog.com/project/1/data-management/sources)), and enabling more is welcomed. **Probe before concluding a table is unavailable**, and if you enable one or find this table wrong, correct it here in the same pass.

**Caveats worth respecting.**

- Queries pass through HogQL as a translation layer; the SQL editor has a Raw SQL toggle top-right, which the MCP path does not expose.
- `SELECT *` does not work; name the columns.
- **`properties` is a plain String here, so dot-access fails.** `properties.$lib` errors with `Can not access property "$lib" on field "properties" of type: StringDatabaseField`. Use `JSONExtractString(properties, '$lib')`. Worth knowing before writing any query that reads a property, since the same SQL runs fine on the project-2 catalog.
- PostHog reserves the freedom to change ClickHouse schemas and column configs liberally. So this is right for the ad-hoc reads a deep dive makes, and wrong to build a persistent saved insight or a customer-facing dashboard on.
- The source config reports `direct_query_enabled: false` while direct queries via `connectionId` work anyway. Observed, not explained; do not build logic on that flag.
- It reads every team's data, so a missing `team_id` filter silently returns PostHog-wide numbers. The half-swap hazard the region rules describe applies here with more force: always filter `team_id` explicitly, and never let a `team_id` cross the region boundary.

### GitHub: the source of truth for mechanism, never for citation

PostHog's product code and docs source are open, so `gh` settles what no query or docs search can: whether a given event is billed. Read `gh api repos/PostHog/posthog/contents/posthog/tasks/usage_report.py --jq '.content' | base64 -d`, then `get_teams_with_billable_event_count_in_period` and its `excluded_events` list, because no docs page enumerates the meters. The emitter, billing code, and ingestion path are readable the same way when a figure contradicts itself and no query explains why. Check availability once with `gh auth status`; optional, skip silently when absent. Code search needs the token's `repo` scope and returns `total_count` 0 rather than erroring on a bad query, so a zero is not proof of absence.

**The boundary, and it is absolute. `docs-search` stays the only citation for anything customer-facing.** The repo holds unreleased and in-review changes, so a `.mdx` file can describe behaviour that has not shipped, and quoting it to a customer ships a promise PostHog has not made. Establish mechanism on GitHub; then cite the published page, or say the docs do not cover it.

### Three kinds of region handling

1. **Split by table name**: `postgres.posthog_*` (US), `eu_postgres_posthog_*` (EU). Pick by `app_region`. Naming exception: the cohort-calculation table is `eu_posthog_cohortcalculationhistory`, with no `postgres` in it.
2. **Combined, region in a COLUMN**: the column name AND the value case both vary per table, so read the distinct values before filtering. `all_posthog_team.app_region` lowercase; `sales_and_cs_customers_30_day_usage.instance` uppercase; `all_postgres_posthog_datamodelingjob.region` uppercase; `llma_sentiment_engagements_last90d.cloud_region` lowercase. Filter positively (`= 'EU'`), never `!= 'US'`, because `signals_scouts_run_events.region` also holds `DEV`.
3. **Region-agnostic** (no prefix, no filter): the org usage report, `postgres.prod.billing_customer`, `revenue.*`, `vitally.*`, the dbt billing tables.

**A region-ish column is often not the cloud region.** `web_pre_aggregated_stats.region_code` / `region_name` and `llma_events.user_region` / `llma_user360.user_region` hold the GEOGRAPHIC region of the end user ("California", "Hesse", "England"), not the EU instance. Read the values before trusting the name.

Counts survive where definitions do not: an EU account is a blind spot for "which ones", not for "how many".

**Actions have no EU source in either project**, probed under every naming pattern. Unmeasurable, not zero. Property definitions DO have one, the direct connection's `property_definitions` table, so do not report them unmeasurable on EU.

**EU flag keys are partially recoverable, so say "evaluated keys" rather than reporting them unmeasurable outright.** `postgres.posthog_featureflag` is US only and `eu_postgres_posthog_featureflag` does not exist, but on the direct connection `$feature_flag_called` carries the key in `JSONExtractString(properties, '$feature_flag')`, filtered by `team_id`. **Read the limit as hard: this returns only flags the SDK actually evaluated in the window, so a dormant, archived, or never-served flag stays nameless, and the count from `ff_count` is still the only complete total.** So the honest sentence on EU is "N flags exist, of which these K were evaluated", never "they have these K flags".

**One EU table is advertised and unreadable**: `eu_postgres_posthog_grouptypemapping` fails with a ClickHouse error on every attempt, including a bare `SELECT count()` with no join, so treat it as none rather than as flaky. `eu_postgres_posthog_dashboard`, `_dashboarditem` and `_dashboardtile` ARE **readable**, so read them rather than routing dashboards through the usage report. `eu_postgres_posthog_proxyrecord` is a different failure, an unknown table, so it errors on name resolution instead. This entry has been wrong before in the direction that manufactures a needless "unmeasurable", so probe before believing any row of it.

**Resolver caveat**: the resolver's "Did you mean" on a missing `eu_` table suggests US tables first (`postgres_posthog_action, postgres.posthog_action, ...`). Never follow a suggestion across the region boundary.

### Event names from saved config (a floor, and now a fallback only)

**Read the real catalog with volumes off the direct ClickHouse connection above, in both regions.** Keep this scrape only for when that connection is unreachable: it returns events they reference in saved config, never events they merely capture, and it carries no volumes at all.

- US: `postgres_posthog_action.steps_json` plus `postgres_posthog_dashboarditem.query`.
- EU: `eu_postgres_posthog_datawarehousesavedquery` plus `eu_postgres_posthog_hogfunction.filters`.

## Reading data without being fooled

## What we can and cannot see

Map the org to its teams first with `all_posthog_team WHERE organization_id = '<ORG_ID>'`. It is cross-region and returns `app_region` (lowercase `us` / `eu`) beside the team ids, so one query gives you both. One org has several teams, some staging or demo.

**Org ids are globally unique. Every integer id is region-local and collides.** Filtering by `organization_id` is always safe; filtering or joining by a bare `team_id` or `user_id` is not, because the same integer names a different company in the other region and the query neither errors nor returns empty. The live danger is the **half-swap**, mixing a US table into an EU query: `eu_postgres_posthog_organizationmembership` joined to `postgres.posthog_user` returns unrelated strangers as this account's owners and admins, which is a contact list you could email. Swap regions all-or-nothing across every table in a statement, and never carry an integer id across the boundary.

| Kind of source | Answers | Region |
|---|---|---|
| The org usage report | how much, how many. Org level and per-team | both |
| The query logs | what they actually use, and what is live vs stale | both |
| The postgres mirror | names, keys, definitions, settings | US complete, EU partial |
| Vitally and the pipeline tables | ownership, stage, MRR, conversations | both |
| `events` filtered by `$group_0` | their team using the PostHog app, NEVER their product | both |
| The direct ClickHouse connection, `team_id` filtered | their product's raw events | both, contents differ |

Counts from the usage report, activity from the query log, names from the mirror. The events row is the trap: an `$autocapture` or `$pageview` count there is the customer's team clicking around PostHog.

**Every mirror count needs `WHERE deleted = false`**, and the exceptions are listed per table in `queries-products.md`, which owns that rule. Those tables keep soft-deleted rows and the usage report does not, so an unfiltered count overstates. Filtered, the two agree exactly, so cross-check them whenever a count drives a recommendation. When a filter errors, read the error rather than the file: the column set is probe-verifiable and this list has drifted before.

**`system.*` app tables (`feature_flags`, `actions`, `experiments`, `cohorts`, `surveys`, `insights`) are scoped to project 2 and return PostHog's own data, never the customer's.** `system.accounts` and `system.account_relationships` are the exception, being cross-org Customer Analytics.

**The project-scoped health tools are unusable from here.** `health-issues-summary` and `health-issues-list` take no project argument, so they describe whatever project the MCP is on, which is project 2. Called from here they return PostHog's own estate, its warehouse failures and its own SDKs, none of it the customer. And there is no way to point it at them: `switch-project` to a customer team id returns **404 Not Found**, because these are other organizations' projects and the token does not reach them. So the eleven server-computed checks those tools expose (`no_live_events`, `sdk_outdated`, `ingestion_warning`, `reverse_proxy`, `no_pageleave_events`, `authorized_urls` and the rest) stay hand-rolled here, and the equivalents in this file are the only route. Do not re-test this hoping for a different answer; the blocker is access, not syntax.

**Never read absence out of `system.information_schema.tables`.** It is incomplete (`posthog.ai_events` holds data yet appears in neither `tables` nor `.columns`) and silently caps at 100 rows without an explicit LIMIT. Probe the candidate table directly and read the resolver's "Did you mean" list, which fuzzy-matches the real tables; its suggestions cross regions (a missing `eu_` table gets US suggestions first), so never follow one across the boundary.

**Work with the tools you have, and name what they cannot reach.** The list is now short: their replay and heatmap tables on US, `query_log_archive` on US, Actions on EU, and flag keys on EU (though flag counts are not). Each is unmeasurable rather than zero, so report it as not readable, say which source would carry it, and turn the gap into a question for the customer. Never gate a finding on a read you cannot perform, and never build the output around one. Per-event volumes, the autocapture share, the identity mix, replay volume, the unqueried-events join and property definitions ARE all reachable on EU through the direct connection, so do not carry the old "EU is a blind spot" habit into a brief.

**The project-2 catalog holds no raw product event stream**, so it cannot answer the event-name catalog and per-event-name volumes (no `eventdefinition` mirror in either region), the autocapture share (no autocapture field in the usage report), `$set` volume and `identify()` per-session frequency (identified share is reachable, call frequency is not), or anything else read off raw events. **Read all of these from the direct ClickHouse connection, in either region**, filtering `team_id` explicitly; the result is the customer's own data, safe to state as a finding. What else that connection reaches differs per region: read the direct-connection section above before using it, for the per-region table, the exact call shape per region, and the rule that these reads are right for evidence and wrong for a persistent customer-facing artifact.

## Traps

- **Session replay, heatmaps and logs do not contribute to event counts, and only replay and logs are actually absent from `events`.** Replay capture is `$snapshot` (dedicated storage) and logs go to the `logs` table, so both really do return ~0 from `events`. **Heatmaps behave the same way**: probed instance-wide across both regions, `$heatmap` and `$$heatmap` together return a handful of rows at most, so they are effectively absent from `events` too and their volume lives in the usage report's `heatmap_events_count_in_period` instead. The practical rule is unchanged: counting any of them in `events` understates by design, so an empty or tiny result is a false negative and never proof the product is off.

**Heatmap volume does not bill, so it never appears in a cost table or a saving.** It is real volume on a real meter-shaped field, which is exactly why it reads like a lever, and a run has come close to shipping a cost recommendation built on it. Pitch heatmaps on value or turn them off for noise; never for money. **From project 2 you cannot read a customer's replay or heatmap data at all**: those tables are scoped by the local project's `team_id` with no org column, so a query returns PostHog's own recordings as a plausible wrong number. From project 2, read the `posthog_team` opt-in booleans for on/off and the org usage report for volume; the report carries heatmap volume only inside its `teams` map (`heatmap_events_count_in_period`), so read it from there; the opt-in boolean alone is never a number. **On the direct connection this splits by region**: EU reads `session_replay_events` and `heatmaps` per `team_id`, US errors on both. Inside a customer's own project, by contrast, the raw table is authoritative: count recordings with `count(DISTINCT session_id)` on `raw_session_replay_events` filtered on `min_first_timestamp`, verify the aggregated view against it before trusting its detail columns, and treat `system.session_recordings` as backend metadata, not analytics.
- **Before calling any product unused, confirm where its data lives.** A documented query returning empty can mean the data sits in a dedicated table rather than `events`. Probe the candidate name directly and let the error decide.
- **Run `hog-functions` in the same round as the event-volume reads, but interpret no count, share or trend until its result is in: look for a sampling or drop transformation.** Transformations run at ingestion, so one dropping events changes the denominator under every count, share and trend you are about to compute, and nothing else in the data announces it. A customer self-installing downsampling on their highest-volume events drops billed volume overnight, which reads as churn or a broken SDK until you find the transformation. It is also a finding worth raising, since PostHog does not scale sampled numbers back up: every insight and dashboard they own now understates reality. Confirm the current billing treatment of dropped events with a docs search before saying anything about the saving.
- **An account is only pulled into onboarding once forecasted MRR passes $500, so the pipeline stage itself carries money information.** On a credit-funded account that is the whole story: the grant is running out and a first real cash invoice is imminent, which is why the account surfaced now rather than a year ago. Lead with the date the credit runs dry and the size of the first cash bill, not the paid-invoice count, and treat the customer as new-to-paying and unbudgeted for it.
- **A forecast field describes the period so far**, so it is worthless in the first days of a cycle and lags on a growing account. Check where today sits in the billing period before quoting one: a line that looks like a collapse is often a fresh cycle rather than a customer change, and on a growing account the forecast can sit barely above the PREVIOUS invoice. Take the last real invoice as the floor, apply the observed growth, and say what the forecast is actually measuring.
- **Validate the pricing model against a real invoice before projecting anything.** Rebuild the last completed period from the published tiers, compare it to what that invoice charged, and only then apply the same ladder to the current period. Agreement earns the right to state a projection; the residual tells you which line you cannot yet price. A mid-period figure quoted as a full-period bill is the specific error this catches.
- **Show the whole money picture, never one number.** `money-picture` returns the list total, the discount, the credit applied, the credit remaining, the runway and the cash actually due in one read. State all of them, because on a credit account every figure misleads alone: the invoice reads one number, the cash due reads 0.00, and PostHog books a third, all true at once. Give the customer that arithmetic plainly: this is your usage, this is what the credit covers, this is what you will actually pay.
- **Filter invoices on `period_end <= now()`, never on `status`.** On a credit-funded account every recent cycle sits in `draft`, so a status filter silently serves a months-old invoice as "their bill".
- **Every MRR field answers a different question.** `accounts_replacement_v2.mrr` and Vitally `forecasted_mrr` are what PostHog books, which on a discounted account is the invoice times (1 minus the discount). Vitally `usage_mrr` is closer to the invoice but misses flat add-ons. Never quote an MRR field as "the bill". The dbt line items are for product mix and spike detection only.
- **Two credit clocks, and they disagree by design.** `credit_runway_days` is how long the credit lasts at the current burn rate; `credit_days_left` is calendar days until it expires. Runway can be weeks while the expiry is months away, so they start paying cash long before the expiry date. Report both, labelled, and lead with the runway: it is the one that surprises people.
- **Surface a source conflict, never resolve it silently.** When two fields that should agree do not, put both values and their sources in the output and say they disagree. Quietly picking one is how a wrong number reaches a customer under a real person's name.
- **Low-trust fields**: `sfdc.harmonic_headcount` / `company_type` / `funding_stage` and the LLM `customer_archetype` are often wrong; trust Clay when they disagree. Vitally `lastSeenTimestamp` is unreliable for activity claims; use event data.
- **Clay** knows who the company is, which PostHog and Vitally never do. Read the free data first (`sfdc.harmonic_*`, `sfdc.Clearbit_*`, `sfdc.Company_tech__c`, per-user `title` / `linkedIn`), then spend credits to verify a suspect profile or fill a gap. Start with `search-companies`; if it returns empty, stop and do not chase contacts at a company Clay does not know (a plan error is plan gating, not a bug). Person lookups (`search-contacts` by role, `search-contacts-by-name`) take a NAME plus company, never an email: derive one from the admin email prefix or search by role, and use a full name, which resolves far better than a surname. Searching people is free; data points are not. `add-company-data-points` / `add-contact-data-points` return a `taskId`, not a value: poll `get-task-context`, and read the empty immediate response as pending, not no-match. Always request the `Email` data point and confirm it equals the one you started from, the only check that the enriched person is the right one before their title lands in a draft. Tech Stack is the highest-value field, because a competing tool is a consolidation pitch invisible from usage data. Skip Clay for solo founders, tiny startups and gmail admins, where it returns nothing.

## Why a session was not recorded

The SDK diagnostic properties ride on their `events`, so the direct ClickHouse connection reads them in either region with a `team_id` filter. Read the combination, not one property: `$has_recording`, `$recording_status` (`active`, `buffering`, `disabled`, `sampled`, `paused`), `$session_recording_start_reason` (`sampled_out`, `linked_flag_match`), `$replay_sample_rate`, `$sdk_debug_recording_script_not_loaded`.

- `$sdk_debug_recording_script_not_loaded`: an ad blocker or CSP is blocking the script.
- **`sampled` and `sampled_out` point in OPPOSITE directions and are not a pair.** `$recording_status = 'sampled'` means the session was **included** by the sample rate and recording started; `$session_recording_start_reason = 'sampled_out'` means it was **excluded** and no recording exists. Reading `sampled` as "dropped by sampling" reports a healthy project as broken, and expecting the two together looks for a combination that should not occur. Either value alone means sampling is working as configured.
- **`disabled` with every other replay property null is a signature, not missing data.** All the trigger and sampling signals are null because the SDK never reached the point of evaluating them: recording is off in project settings or via SDK config, so nothing downstream ran. Do not report it as unexplained.
- `buffering` with no flush: `/s/` ingestion is blocked, usually a proxy or custom-domain mismatch.
