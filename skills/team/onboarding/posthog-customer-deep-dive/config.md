# Config (per user)

The shared defaults, shipped as-is and replaced on every plugin update. Your own values live in `~/.claude/posthog-customer-deep-dive.local.md` (or `config.local.md` beside this file on an older install), which the skill reads on top of this one. On first run Setup probes the tool list and the env, confirms what it found in one message, asks only what it cannot detect, and writes your values there, never here (Setup in `SKILL.md`). A required value reading `<SET THIS>` means ask before the step that needs it. Optional rows set to `none` (or a missing tool) are skipped silently, never logged as an error.

## Required tools

| Tool | Needed for | How to find it |
|---|---|---|
| PostHog MCP with access to project 2 (PostHog App + Website) | every read: Customer Analytics, the onboarding model and its workflows, the email sync, billing, product usage and the app database, except an EU customer's raw product events, which go over the API with `POSTHOG_PERSONAL_API_KEY_EU` (the direct-connection section in `references/data-rules.md`) | surfaces as ONE exec-style gateway tool (search your tool list for "posthog" or "exec"); usage is `info <tool>` then `call <tool> <json>`. Ignore a server literally named "posthog" that lacks the exec command (usually an unauthenticated duplicate). If the gateway tool is unreachable in a session, fall back to the direct API with `POSTHOG_PERSONAL_API_KEY` (see "Execution fallback" in `references/data-rules.md`); the MCP stays primary |

## Keys (env vars)

| Key | Needed for | Required? |
|---|---|---|
| `POSTHOG_PERSONAL_API_KEY` | the direct connection to a US customer's own events (Round 1a's `customer-hosts` runs there), and the fallback for project 2 when the MCP gateway is down | Required |
| `POSTHOG_PERSONAL_API_KEY_EU` | Two things, both on EU project 1: experiment definitions, and the **direct ClickHouse connection** that returns an EU customer's own raw product events (per-event volumes, autocapture share, identity mix). The US key 403s on `eu.posthog.com`, so mint this one in the EU instance. Without it, report both as unavailable rather than reading the gap as zero | For EU accounts, and it is what makes an EU deep dive as complete as a US one |

## Optional context sources

One row per job, tool-agnostic: the skill asks for "meeting transcripts" and this table says which tool answers on this machine. Swap the "Yours" cell for whatever you run (examples in the middle column), naming the exact tools so a session can call them without guessing; `none` skips the source.

| Category | Examples | Yours |
|---|---|---|
| Slack search | Slack MCP | Slack MCP: `slack_search_public_and_private`, `slack_read_channel`. Some bot messages (alerts, digests) come back empty from search even with bots included; read their text through `slack_read_thread`. Search stems words (an account called "Quillmoor" also matches "quill"), so quote the account name and check each hit names it |
| Meeting transcripts | Gong (default; everyone at PostHog records there), a local notetaker | Gong MCP (`mcp__gong__*`), the default. **One probe: `search_calls_by_account` on the domain, with `maxCalls` set high (5000) and a window covering the account's life; on a public email domain (gmail.com, outlook.com) search `search_calls` with `participantEmails` on the exact address instead, since the domain matches every other customer on it. Zero hits ends the source, and "searched Gong, zero calls" is the finding.** A domain miss is not proof nobody met them: before writing it, search once more with `participantEmails` on the deal owner's or the last PostHog host's address. Windows before July 2025 have returned 404, so start an account-life window there. The default cap of 500 truncates the scan and still prints "No matching calls", and a probe that times out is not zero either: say Gong did not answer, and retry once with a narrower window, then cover the rest of the account's life in further windows so no stretch goes unscanned. Measured: a no-result search that ran eight rolling sweeps plus keyword searches spent 64 calls establishing what the first one already showed. Only on a hit do the rest apply: `search_calls` with `customerName` (account name, email domain, or title substring) or `participantEmails` plus a `fromDateTime`/`toDateTime` window and `scope: External`, then `get_call_summary` for the AI outline and `get_call_transcript` for verbatim speaker-attributed text. **The transcript tool pages: pass a large `maxLength` (100000 returns most calls whole) and loop on `offset` until the "showing X of Y" total is reached, or the run reads the first third of a call and thinks it read it all.** Attendees can appear twice (a bare first name with role Unknown beside the email with role External), and the speaker label can be wrong outright (one customer's name on every line, including someone introducing themselves): treat duplicates as one person and check attribution against the call's own introductions and the notes before quoting anyone. The AI outline from `get_call_summary` is worse on both counts: it puts one person's line in another's mouth and expands acronyms wrongly, so quote from the transcript and use the outline only to find the passage. Gong is the only transcript source unless `config.local.md` names a local notetaker for calls you recorded yourself |
| Meeting notes folder | any local folder of call notes, or a local notetaker | `none`. A local notetaker goes in your personal config as its tool prefix, the call that searches it and the call that returns a transcript |
| Gmail (full email bodies) | the claude.ai Gmail connector, `gog` | Gmail connector: `search_threads` on the thread's exact subject, then `get_thread`. `gog gmail search` works the same. **Only for a thread `conversation-history` already tied to the account, and only after checking the recipient domain is the account's**: a first-name search once matched another customer's thread. It reads your own mailbox, so a thread a teammate sent lives in theirs; say so rather than guessing its body |
| Work calendar | Google Calendar MCP (default), `gog` CLI | **Use `list_events`, never `search_events`**. `search_events` takes no time window and is the reason this row used to need a CLI. `list_events` takes `calendarId` (the Work calendar ID from Values), `startTime`/`endTime` as ISO 8601, `orderBy: startTime`, `timeZone` (from Values) and `pageSize`; page on `nextPageToken`. The payload is the `description` field, which carries the Calendly booking-form answers verbatim (role, what they want from PostHog, KPIs, reschedule reason) plus `attendees` and the call link, everything call prep reads. Drop `eventType: OUT_OF_OFFICE` entries and any summary starting `[30-minute buffer`, both of which are noise, not meetings. Already have `gog` set up? `gog calendar events --account <Work calendar ID> --all --from YYYY-MM-DD --to YYYY-MM-DD --max 50 --sort start --timezone <Timezone>` returns the same thing; `--from`/`--to` are the window flags (`--start`/`--end` do not exist) and `--all` is needed or team calendars are missed. A call on a teammate's calendar (they run it, you prep it) is read by passing their address as the calendar id: `calendarId` on `list_events`, or positionally on `gog calendar events <their address> --account <yours> --from ... --to ...`; `gog` has no `--calendar` flag. The MCP is the default because it needs no CLI, no Google Cloud project and no weekly token refresh, so nobody has to set `gog` up just to get a calendar; `gog` earns its setup on Gmail, which this row does not use |
| Enrichment | Clay | Clay MCP: `search-companies` + `get-task-context` (UUID prefix); enrichments cost credits, ~20-100 per invocation |
| Source and docs repos | GitHub CLI | `gh`, authenticated with `repo` scope. Reads the billable-meter definitions in `PostHog/posthog` and the docs source in `PostHog/posthog.com`, and checks whether a customer's request has an open issue or PR. Never the citation for a customer-facing claim (see the GitHub section in `references/data-rules.md`) |

> Publishing note: this file is shared as-is and needs no scrubbing, because personal values belong in your personal config, which the skill overlays on top of this one. Three keys are personal and live there: the work calendar ID, the timezone, and the meeting notes folder. **Do not blank the other "Yours" cells.** The Gong paging procedure, the `gog` flag list, the Slack tool names and the Clay and `gh` notes are the same for everyone at PostHog, and each one records a mistake somebody already made, so wiping them makes the next person rediscover it. Personalise a cell only where it names your machine.
